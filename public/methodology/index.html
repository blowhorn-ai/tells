How Tells scores

This is the methodology for the number Tells returns. It says how the 0-100 score and the pass, warn, and fail verdict are decided, and which version a score belongs to. The points and the rule for each check live in the catalog. This page links that catalog. It does not repeat it.

The score and the verdict

The score runs from 0 to 100. It starts at 100. Each finding subtracts points. The result is kept inside that range.

Three bands turn the score into the report verdict:

  • 75 and up is likely_human. The page says Looks human. Risk is low.
  • 45 to 74 is suspicious. The page says Hard to tell. Risk is medium.
  • Under 45 is likely_bot. The page says Looks like a bot. Risk is high.

A run carrying a high severity finding is at most suspicious, whatever the score: a high finding never reads as human. A run with no pointer or key input observed is reported as no input, not as automated input: it warns, and it costs no points. The verdict card says nothing here reads as a bot only when the report carries no findings; when findings exist, it names the top one instead.

Each check is its own pass, warn, or fail verdict, separate from that band. The labels on the page are Pass, Warning, and Fail:

  • Pass: the readings arrived and no finding matched.
  • Warning (warn): a medium or low severity finding matched.
  • Fail: a high severity finding matched.
  • Not available: the readings never arrived. That is a gap in coverage, not a failure.

When several findings match one check, the row shows the worst severity. How many points each finding subtracts is in the check guide, one page per check, and in the catalog linked below.

Scoring happens on the server

The browser collects readings and posts them. The Worker scores the report and returns it. Scoring happens on the server. A score or a check status that the browser sends is not the verdict. The Worker derives the behaviour score, the interaction checks, and the fingerprint classes again, and the verdict uses those derived values.

GET /api/check scores the request alone: headers, IP reputation, TLS, and managed bot signals. It does not use browser readings. POST /api/report scores the posted readings together with that request. schema_version is on the success body of GET /api/check and POST /api/report. An error body is not that document. Download JSON and Copy JSON are the /api/report success body, so a saved report carries schema_version.

The check body is schemas/check.schema.json. The report body is schemas/report.schema.json.

Which version a number belongs to

schema_version is 1. It names the report contract, the two schemas above. It changes only when that contract breaks. Numbers from an older schema_version are not on the new scale.

The check catalog, schemas/check-catalog.json, has catalog_version. catalog_version is 1.0.3. It is the semver of that file. The file lists every check and every scored reason that already ships. catalog_version is not a field on /api/report. The changelog records each catalog version.

When two scores can be compared

Scores are only comparable across the same schema_version, and across the same catalog when you cite a check. A 90 on one schema_version is not the same claim as a 90 on another. A check you name is not the same check once catalog_version changes what it reads or how many points it subtracts.

To diff two saved reports, open /compare/. When schema_version is missing or the two versions differ, that page warns and still diffs the fields that overlap. The warning and the diff live there.
